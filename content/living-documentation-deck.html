Doc as Code and operational evidence

Living Documentation

Closing the gap between intended software and delivered software

Doc as Code makes software intent machine readable.
Living Documentation reconciles that intent with delivered and observed reality.
Software documentation usually captures what we intended to build. Delivery and production then create additional realities. Living Documentation connects them. Doc as Code is the enabler because it makes architecture, contracts, decisions, journeys, and examples versioned and machine readable. The larger opportunity is to reconcile that intent continuously with evidence from code, delivery, and observability.
The persistent gap

Documentation loses authority as software keeps changing

Intended software
Designed

Domain knowledge, architecture, contracts, journeys, decisions, and policies describe the expected system.

Delivered software
Evolving

Code, configuration, infrastructure, dependencies, and production behavior continue to move.

The problem is not missing documentation alone. The deeper problem is the missing connection between intent and evidence.

Teams often document the domain and architecture carefully at the start. Delivery then changes the implementation, configuration, dependencies, and runtime topology. Manual pages cannot keep up. The important gap is not simply freshness. Teams lack an explicit connection between what they intended and the evidence of what they delivered.

I use three views to explain the model. Intended software captures what we meant to build. Delivered software records what code and artifacts reached an environment. Observed software shows actual runtime behavior. Each view answers a different question. Living Documentation connects them through stable identifiers and provenance.

Doc as Code is more than writing Markdown. Domain models, architecture descriptions, API and event contracts, journeys, and examples can all carry structured intent. Git becomes the source of truth for that intent. Pull requests review it, automation validates it, and GitOps can connect it to delivery. These digital contracts give Living Documentation reliable material to reconcile with implementation and runtime evidence.
What living means

Living Documentation is a reconciliation capability

Intent

Versioned models, contracts, journeys, decisions, and policies

Delivery evidence

Commits, builds, tests, artifacts, deployments, configuration, and flags

Runtime evidence

Topology, telemetry, SLOs, anomalies, incidents, and recovery actions

Visible and explainable divergence matters more than perfect synchronization
The word living should have a precise meaning. Automation refreshes the view. Every statement retains its source, version, environment, and observation time. The system exposes divergence between intent and evidence. Some differences are planned or temporary. Others reveal missing documentation or defects. The objective is to make the difference visible and explainable.

Continuous comparison

Drift becomes visible before it becomes a surprise

  • Contract drift: an operation exists in code but not in the OpenAPI or AsyncAPI definition
  • Architecture drift: runtime calls reveal a dependency absent from the intended model
  • Delivery drift: the deployed artifact differs from the expected Git revision or configuration
  • Operational drift: a critical journey has no useful SLO, telemetry, owner, or current runbook
Once intent and evidence use common identifiers, the platform can surface meaningful drift. It can find contract differences, unexpected runtime dependencies, deployment mismatches, and gaps in operational readiness. The output should not become a noisy compliance report. Each finding needs context, an owner, and a way to record a planned exception.
The proving ground

Incident investigation needs the system context that alerts cannot provide

What was expected?
What is happening?
What changed?
What explains the difference?
  • Affected journeys and business capabilities
  • Current topology and observed dependencies
  • Recent code, configuration, infrastructure, and flag changes
  • Artifact versions and source revisions
  • Related contracts, SLOs, dashboards, and runbooks
  • Owners, correlated telemetry, and past incidents
Incident response is a strong first use case because fragmented knowledge has an immediate cost. A Living Documentation hub can assemble a context pack when an incident begins. It connects the symptom with affected journeys, current topology, recent changes, deployed versions, contracts, SLOs, runbooks, owners, and telemetry. The investigation then follows four questions: what was expected, what is happening, what changed, and what evidence explains the difference?
Historical reconstruction

The system time machine shows which reality applied at the moment of failure

Expected state

Applicable models, contracts, SLOs, and policies

Last known good

Versions, topology, configuration, and observed behavior

First symptom

Changes, anomalies, affected journeys, and blast radius

Recovery

Interventions, restored behavior, and evidence of stability

The feedback loop: incidents update architecture, contracts, tests, runbooks, and observability requirements.
Current state is not enough for incident analysis. Responders need the models, versions, configuration, topology, and telemetry that applied when the first symptom appeared. A system time machine can compare the last known good state with the failing state and the recovery. Incident findings should then flow back into architecture, contracts, tests, runbooks, and observability requirements.
AI across the lifecycle

AI becomes useful when it can reason over connected evidence

  • Which customer journeys could this change affect?
  • Why does observed topology differ from the C4 model?
  • What changed immediately before the latency regression?
  • Which contracts, tests, dashboards, and runbooks relate to this service?

Grounding requirements

Provenance: point to the authoritative source

Context: retain version, environment, and time

Epistemics: separate facts, inferences, and hypotheses

Security: inherit access controls from each source

As code makes every lifecycle stage machine readable, AI can participate continuously from discovery to production evidence. The strong opportunity is not a chatbot placed in front of disconnected tools. It is a connected evidence model. AI can answer cross system questions and propose hypotheses, while every answer retains provenance, time, environment, and a clear distinction between fact and inference.
A practical first step

Begin with an incident lens over one critical journey

  1. Choose a bounded domain or important customer journey
  2. Version its architecture, contracts, decisions, and examples
  3. Connect services to owners, deployments, dashboards, and runbooks
  4. Capture changes as time stamped delivery evidence
  5. Compare intended dependencies with observed topology
  6. Generate an incident context pack and measure the investigation

Doc as Code makes software intent versioned, reviewable, and machine readable.

Living Documentation continuously reconciles that intent with delivered and observed reality.

The first product does not need to be an enterprise documentation portal. Start with one bounded domain or critical journey. Put its intent under version control, connect it to delivery and operational evidence, compare intended and observed dependencies, and generate an incident context pack. This creates immediate operational value while building the connected model that architecture, compliance, delivery, and AI can reuse.
