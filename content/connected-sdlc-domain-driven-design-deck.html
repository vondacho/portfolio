Semantic contract

Language applies inside an explicit boundary

A term, rule, or model is precise only within the bounded context that gives it meaning.

A global glossary can create false consistency. The same word may mean different things in different contexts. The model must scope language explicitly.

Sources: Eric Evans, DDD Reference and Context Mapping as Code.

Bounded contexts give domain language a precise scope.

Strategic and tactical design

Two connected levels of the model

Strategic

Subdomains, bounded contexts, ownership, and context relationships.

Tactical

Aggregates, entities, value objects, events, policies, and invariants.

Strategic design protects boundaries and relationships. Tactical design expresses behavior within a context. The two levels should link rather than become separate diagrams.

Git and GitOps

Git as source of truth and semantic reconciliation

Git sourceContexts, language, invariants, policy
Review and mergeDomain and affected owners approve
AutomationPublish maps, catalogs, checks
ReconciliationFind semantic and dependency drift

Git holds the accepted semantic model and its history. Review rules bring the appropriate domain, supplier, customer, architecture, and development owners into meaningful changes.

GitOps-style automation publishes the model and compares code, contracts, examples, and architecture with it. Retired terms or forbidden dependencies become visible without letting automation redefine domain meaning.

Source: OpenGitOps principles.

Git governs accepted domain meaning. Automation publishes it and detects semantic or dependency drift.

Change management

Begin with one painful boundary

01Choose

Select a core domain with recurring ambiguity.

02Model

Name contexts, owners, language, and one key invariant.

03Connect

Link events, stories, examples, and architecture.

04Protect

Add one valuable boundary rule in CI.

Focus on a real boundary problem. Provide visual editing for domain participants and IDE feedback for developers. Expand when teams experience reduced ambiguity or integration risk.

Sources: Eric Evans, DDD Reference and Context Mapping as Code.

Start with one boundary, one model, and one enforceable rule.
