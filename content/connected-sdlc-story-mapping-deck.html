Ticketing contract

The Story Map supplies contextualized tickets

Story Map ownsOutcome, journey position, story scope, release slice
Ticket inheritsStable ID, pivotal events, rules, examples, model revision
Ticket ownsAssignee, workflow state, sprint, delivery timestamps

This ownership rule prevents two sources of truth. The map owns product meaning. Ticketing owns operational workflow. Shared fields follow a defined synchronization policy.

Sources: Jeff Patton, User Story Mapping and Story Mapping as Code.

Git and GitOps

Git as source of truth and ticket reconciliation

Git sourceJourney, stories, slices, references
Review and mergeProduct owners accept delivery intent
Ticket projectionCreate and update governed fields
ReconciliationDetect drift without losing workflow data

Git holds the accepted Story Map revision. GitOps-style automation pulls it and reconciles the product fields that the map owns, including journey position, scope, slice, and contextual references.

Ticketing continues to own assignment, workflow state, sprint data, comments, and delivery timestamps. The ownership policy prevents synchronization from overwriting operational work.

Source: OpenGitOps principles.

Git governs journey and release intent. Automation aligns ticket context while ticketing retains workflow state.

Change management

A safe migration from backlog-first delivery

01Map

Reconstruct one active journey from current work.

02Generate

Create new tickets from the accepted map.

03Link

Add examples, contexts, and components.

04Synchronize

Automate only after ownership is clear.

Begin with one release and one-way ticket generation. Keep delivery fields local. Add controlled synchronization only after the team trusts the source relationship.

Sources: Jeff Patton, User Story Mapping and Story Mapping as Code.
