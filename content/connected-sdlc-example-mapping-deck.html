As-Code in practice

The visual map has a declarative source

examplemap "Title" {
  story "Redeem a voucher" {
    as   "Returning customer"
    want "to apply a voucher code at checkout"
  }
  rule "A voucher must not be expired" {
    example "A voucher that expired yesterday is refused" {
      given "a voucher SUMMER10 that expired on 2026-08-21"
      when  "the voucher is applied"
      then  "the voucher is refused"
    }
  }
}

Notation protects syntax. Doctrine protects the practice.

This fragment uses the supplied Example Mapping notation. It records the story, a rule, and a concrete example. The given, when, and then lines make the example suitable as input to executable acceptance work.

Git and GitOps

Git as source of truth and behavioral reconciliation

Git sourceAccepted rules, examples, questions
Review and mergeProduct, domain, QA, development
AutomationGenerate scenarios, fixtures, mocks
ReconciliationCompare tests and evidence with intent

Git holds the reviewed Example Map revision that developers, QA tooling, and AI must use. GitOps-style automation pulls it, generates permitted test assets, runs relevant checks, and links the evidence back to its source.

Executable tests can reveal a difference, but they do not silently redefine intended behavior. Product and domain participants decide whether the contract changes.

Source: OpenGitOps principles.

Change management

Adoption begins with misunderstood stories

01Select

Choose stories with recurring defects or debate.

02Map

Run a short cross-functional conversation.

03Generate

Publish ticket acceptance and scenario skeletons.

04Trace

Link test results back to examples.

Do not add another ceremony to every story. Start where ambiguity is expensive, generate artifacts teams already need, and add traceability step by step.
