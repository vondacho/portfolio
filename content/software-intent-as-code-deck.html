Software Intent
as Code

A machine-readable specification backbone from Big Picture discovery to tickets and running software

Event Storming · Story Mapping · Example Mapping · Context Mapping

Documentation as Code improved how we maintain technical documentation. I want to extend the same discipline to the intent that exists before code: the user journey, domain discoveries, business rules, system boundaries, and design decisions.

The proposition is a machine-readable specification backbone for the whole software development lifecycle. Event Storming moves from Big Picture to Process Modelling and System Design. Story Mapping becomes the delivery spine and source for ticketing. A normalized representation evolves behind each board and becomes usable by developers, engineering tools, and AI.

The idea extends Documentation as Code to software intent. Event Storming, Story Mapping, ticketing, design, and validation connect through a normalized model.

The handoff problem

Intent loses detail each time people translate it

WorkshopRich discussion and spatial context
Board photoVisible result without explicit semantics
DocumentSelected decisions and summaries
BacklogWork items separated from reasoning
CodePrecise behavior with partial intent
TestsEvidence that may miss the original outcome

Our practices are already strong. The weakness appears between them. A workshop contains domain language, disagreement, reasoning, and unresolved questions. A photo preserves the layout but not the semantics. Documentation selects part of the result. Tickets divide it into work. Code becomes precise, but the original reasoning becomes difficult to recover.

AI inherits the same problem. If we give an agent screenshots, prose, and disconnected tickets, it must infer relationships that the team already discovered. A plausible implementation may still violate an unstated rule or boundary.

The lifecycle repeatedly translates the same intent. Each handoff can drop relationships, decisions, and uncertainty. AI cannot recover reliably what the organization failed to preserve.

The important design choice is to separate the human projection from the structured model without splitting them into different sources of truth.

People need the board because spatial arrangement, color, and conversation support discovery. Machines need explicit types, identifiers, and relationships. When these two representations remain synchronized, developers, IDEs, generators, test tools, and AI all receive material grounded in the same validated intent.

The board supports human cognition. The normalized model gives developers, engineering tools, and AI the same validated material.

Event Storming at three levels

One practice connects domain landscape, process, and system

01Big Picture

Explore the wider domain, shared language, hotspots, and pivotal events.

02Process Modelling

Follow an outcome through commands, events, policies, actors, and exceptions.

03System Design

Shape software behavior, domain rules, responsibilities, and integration points.

Event Storming is more than a Big Picture workshop. The Big Picture creates shared situational awareness across the wider domain. Process Modelling then narrows the focus to an end-to-end business outcome. System Design adds the detail needed to decide how software handles commands, produces events, applies policies, and protects domain rules.

As-Code preserves continuity across these levels. A hotspot can become the scope of a process model. That process can acquire System Design detail without losing the language and events already validated.

Event Storming connects Big Picture, Process Modelling, and System Design. As-Code preserves the same language and decisions as the work gains precision.

Behavioral precision

Examples make intent testable

A story becomes useful to delivery when rules, concrete cases, and uncertainty are explicit.

StoryChange a paid booking
RuleThe new option must still be available
ExampleA seat opens before confirmation, so the change succeeds
QuestionWhat happens when the price decreases?

Story titles compress too much. Example Mapping gives the team a disciplined way to expose the behavior behind a story. Rules describe constraints, examples make them concrete, and questions preserve uncertainty.

Once represented as code, these elements can support acceptance criteria, test design, and AI-assisted scenario exploration. A coding agent can receive approved examples as explicit constraints. A QA specialist can find rules without executable evidence or challenge AI-suggested edge cases.

Rules and examples turn intent into explicit behavioral constraints. They guide implementation and provide evidence for judging AI-generated code.

Behavior alone does not say where responsibility belongs. Context Mapping connects discovery to ownership and system design. A domain event belongs to a bounded context. That context has relationships with other contexts and, often, a team accountable for its evolution.

Domain models add concepts and invariants inside the boundary. LikeC4 and PlantUML artifacts can show how components realize the design. The as-code approach allows these views to carry references forward without forcing every practice into the same notation.

Context Mapping adds responsibility and integration boundaries. Domain models and architecture-as-code views connect those boundaries to software components.

Git and GitOps

Git source of truth and lifecycle reconciliation

Visual toolsPeople explore and change the model
Git sourceAccepted intent and full history
ReviewOwners approve meaning and impact
AutomationValidate, generate, publish
ReconciliationDetect drift and propose change

Git provides the authoritative record for accepted software intent. People can keep working through Event Storming, Story Mapping, Example Mapping, Context Mapping, and architecture views. The tools commit the normalized models behind those views, and a merge identifies the revision that downstream consumers should use.

GitOps extends the repository into an operating loop. Automation pulls accepted intent, validates contracts, regenerates permitted projections, publishes their source revision, and detects drift in tickets, tests, architecture, code, or the running system. Safe projections can update automatically. Changes to business meaning, release scope, or responsibility return to people for review.

Source: OpenGitOps principles.

Git records accepted intent. GitOps automation publishes its projections and surfaces drift while people retain authority over meaning.

Conditions for scale

Trust requires explicit governance

Generation is easy. Preserving meaning across people, tools, and time is the hard part.

Stable identities that survive renaming
Versioned schemas and transformations
Provenance for human and AI changes
Clear authority when views disagree
Feedback from tests and operations

Everything as Code can still create drift if every generated artifact claims authority. A trustworthy backbone needs stable identifiers, versioned schemas, transformation provenance, and explicit ownership.

Round-trip editing also needs careful conflict handling. A person may change the visual board while another changes the coded representation. The tool must surface disagreements. Finally, evidence from tests, contracts, and operations should reveal where the specification and the running system diverge. These guardrails make the scale proposition credible.

Scale depends on identity, versioning, provenance, authority, and feedback. These controls prevent connected as-code artifacts from becoming a more sophisticated form of drift.
