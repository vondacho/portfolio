Visual collaboration · As-Code contracts · Git source of truth · GitOps reconciliation

AI-driven software development is often reduced to faster code generation. This deck starts earlier. It treats the user journey, domain discoveries, product choices, behavioural examples, boundaries, and architecture as machine-readable inputs to delivery.

Software Intent as Code provides the integration layer that lets AI boost the entire SDLC. People work through visual tools. Git records accepted intent. Automation and AI operate on the same structured models from discovery to production evidence.

Software Intent as Code lets AI boost the full lifecycle because intent becomes machine-readable before code generation begins.

The current starting point

Code generation begins after most design decisions

The agent receives

A repository, a flat ticket, scattered prose, and implementation patterns.

The agent must infer

User outcomes, domain rules, bounded contexts, architecture constraints, and proof of correctness.

A coding agent can produce plausible code from a repository and a ticket. The repository mainly shows what the system has become. The ticket compresses the reasoning that led to the change.

The agent must reconstruct product intent, domain language, business rules, system responsibility, and acceptance evidence. Improving the final prompt helps, but preserving those decisions throughout the lifecycle creates much more leverage.

A repository and a ticket rarely contain enough explicit intent for dependable AI-assisted delivery.

The generation contract

Three instructions make AI practice-aware

Doctrine

Practice intent, quality signals, preserved uncertainty, and decisions AI must not make.

Notation

Modelling elements, relationships, annotations, and their visual meaning.

DSL

Exact grammar and file format that generated output must satisfy.

Notation protects syntax. Doctrine protects the practice.

These documents are explicit, versionable instructions for the LLM. Doctrine constrains the meaning and protects the intent of the practice. Notation explains the model constructs and their visual semantics. The DSL defines the exact source format and enables parser validation.

Together they prevent a common failure: syntactically correct AI output that damages the practice by resolving uncertainty, inventing facts, or smoothing away meaningful disagreement.

Doctrine governs meaning, notation explains the model, and the DSL constrains the exact generated file.

Each practice publishes a complete instruction set for AI. The links are deliberately visible in the deck so a team can inspect the exact rules that govern generated models.

Because these instructions are addressable and can be versioned with the models, every proposal can record which doctrine, notation, and DSL revision shaped it. That provenance makes AI behaviour reviewable and reproducible.

Each practice exposes doctrine, notation, and DSL as inspectable, versionable instructions for the LLM.

The prompt is only one input. AI also needs the current accepted model and the applicable doctrine, notation, and DSL instructions.

The result should normally be a reviewable proposal or diff with provenance. Automated checks establish that it is well formed and satisfies enforceable semantics. People decide whether it is true, useful, and ready to become the next accepted revision in Git.

AI proposes against the instruction set; validation checks it; people decide whether it becomes accepted intent.

AI-driven discovery

A user journey becomes a structured hypothesis

Journey promptUser, need, desired outcome
Big PictureEvents, actors, systems, hotspots
Expert reviewLanguage, assumptions, missing behaviour
Focused modelsProcess Modelling and System Design

A prompt can seed an Event Storming Big Picture instead of producing another prose document. AI proposes a structured domain hypothesis containing events, actors, external systems, hotspots, and open questions.

Experts correct the model and select the areas that require deeper Process Modelling or System Design. The value comes from the combination of rapid generation and collaborative correction.

Tool: Event Storming as Code.

AI seeds the model. Experts turn the hypothesis into credible domain knowledge.

Event Storming

Progressive precision across three scopes

Big Picture

Domain landscape, language, hotspots, and pivotal events.

Process Modelling

Commands, events, policies, actors, exceptions, and dependencies.

System Design

Software behaviour, responsibility, rules, and integration points.

Event Storming provides continuity from broad discovery to software detail. The Big Picture creates shared situational awareness. Process Modelling develops one outcome. System Design adds the precision needed to shape software.

As-Code preserves the same events, language, decisions, and stable identities as the model matures. AI can propose omissions or connections without erasing the distinctions between the scopes.

Event Storming moves from landscape to process to software responsibility without losing the earlier discoveries.

Story Mapping

The Story Map governs delivery context

Map ownsUser outcome, journey position, story scope, and release slice
Ticket inheritsStable ID, pivotal events, rules, examples, contexts, and source revision
Ticket ownsAssignee, workflow state, sprint data, comments, and delivery timestamps

Pivotal events connect domain discovery to the Story Map backbone. The map preserves the user journey and defines coherent release slices. It becomes the source for product and release meaning.

Ticketing remains the operational workflow system. Generated tickets inherit context from the map while retaining local workflow data. AI can reason about a release as a journey rather than a bag of independent work items.

Tool: Story Mapping as Code.

The Story Map supplies product meaning. Ticketing coordinates execution.

Product, domain, QA, and development participants decide which examples express intended behaviour. Executable tests provide evidence. They do not silently redefine the accepted specification.

Domain-Driven Design

Language and responsibility need explicit boundaries

Strategic model

Subdomains, bounded contexts, ownership, and context relationships.

Tactical model

Aggregates, entities, value objects, domain events, policies, and invariants.

DDD supplies the semantic contract. It determines where language applies, who owns the model, how contexts relate, and which invariants the software must protect.

AI can detect inconsistent terminology, suggest boundary candidates, and identify affected owners. Domain experts and engineers decide whether the model supports the business effectively.

Tool: Context Mapping as Code.

DDD tells developers and AI which meaning applies and where responsibility belongs.

C4 and LikeC4 express architecture at useful levels of abstraction. PlantUML adds focused behavioural or structural views. Technical contracts define the integration surfaces.

AI can now see which component may change, which dependencies are allowed, which contract needs compatibility analysis, and which scenario or operational signal provides evidence. Architecture becomes active material in delivery.

Architecture and technical contracts give AI explicit implementation limits and compatibility obligations.

GitOps extension

Accepted intent becomes an operating loop

DeclareMachine-readable models and policies
ReviewOwners approve meaning and impact
AutomatePull, validate, generate, publish
ReconcileDetect drift and propose change

GitOps principles extend naturally to the specification lifecycle. The accepted models declare intent. Automation pulls the approved revision, validates digital contracts, and publishes the permitted projections.

Reconciliation compares tickets, tests, architecture, code, and runtime evidence with the declared state. Safe generated outputs can update automatically. Changes to meaning, product scope, domain boundaries, or architecture responsibility return to people for review.

Source: OpenGitOps principles.

GitOps keeps consumers aligned with accepted intent without transferring decision authority to automation.

Digital contracts

As-Code makes lifecycle checks explicit

Schemas protect artifact structure
Semantic checks protect meaning and references
Compatibility policies protect interfaces
Ownership rules request the right reviewers
CI blocks invalid committed models
Evidence reports the exact source revision

As-Code enables enforcement, but serialization alone does not enforce a contract. Schemas, semantic validators, compatibility policies, review rules, and CI perform the enforcement.

The strength of checks should match decision maturity. Discovery tolerates uncertainty. A committed release or public contract needs stronger guarantees. This protects exploration without weakening delivery.

Validation becomes stronger as decisions move from discovery into committed delivery.

Engineering material

The developer receives more than a ticket

Journey, events, rules, examples, boundaries, architecture, and contracts arrive together.

IDEs, generators, validators, tests, and AI consume the same accepted specification.

This is the immediate developer value. The ticket remains the unit of delivery workflow, but it carries stable references to the material that explains why the change exists and what must remain true.

As-Code gives developers and their tooling the right material to do the right thing. AI then works from the specification the team already validated. Better inputs make generated changes easier to constrain, test, explain, and review.

Developers, engineering tools, and AI work from the same validated intent.

Adoption requires a change in daily work. The facilitator or architect cannot maintain every artifact for everyone else. Meaning stays with domain and product participants. Development, quality, and architecture maintain the connected engineering contracts. Platform teams make the workflow easy.

The wiki remains useful for learning, rationale, and publication. It no longer acts as the first-class source for current behavioural or architectural truth.

Shared ownership keeps As-Code inside normal work instead of creating another documentation role.

Change management

Adoption begins with one connected thread

01Select

Choose one value stream where context repeatedly disappears.

02Connect

Link one pivotal event, slice, ticket, examples, and component.

03Automate

Remove one manual translation that the team already performs.

04Enforce

Add high-value checks after ownership and semantics are clear.

Start with one end-to-end thread and one immediate benefit. Generate ticket context, publish an architecture view, create scenario skeletons, or detect broken references.

Do not begin with an enterprise mandate to model everything. Expand after participants trust the workflow and the generated outputs save time. Measure translation time removed, broken handoffs detected, and changes understood earlier.

Prove the connected flow on one value stream, then add automation and enforcement progressively.
