# From Handoffs to Shared Intent --- LinkedIn Saga

## 1. The Change Is Not the Tool

Contract-Driven Development is not primarily a tooling transformation.

It changes how people collaborate.

In a traditional delivery flow, knowledge often moves through handoffs:

**BA → requirements → Dev → implementation → QA → validation**

Every handoff creates interpretation.

CDD suggests a different center of gravity:

**BA + QA + Dev → shared intent → executable agreement →
implementation + evidence**

The roles do not disappear.

Their expertise meets earlier.

BA helps make intent difficult to misunderstand.

QA challenges the agreement before implementation makes mistakes
expensive.

Developers design against clearer expectations and verify continuously.

So perhaps the first change-management principle is simple:

**Don't transform the roles. Transform the collaboration.**

## 2. The BA Becomes a Curator of Intent

Does Contract-Driven Development make the Business Analyst less
important?

I think it can make the role more important.

But the emphasis changes.

From:

**Gather → Document → Hand over**

Toward:

**Discover → Model → Clarify → Example → Maintain intent**

Journey Maps, Story Maps, Event Storming, Example Mapping, domain
language, rules and decisions become connected expressions of intent.

Some of that intent will eventually cross a threshold:

**This is no longer only something we believe or propose. It is
something the delivered system is expected to preserve.**

That is where executable contracts begin.

The BA's contribution is therefore not simply to write more detailed
requirements.

It is to help make the intent **difficult to misunderstand**.

And in an AI-assisted world, that becomes even more valuable.

## 3. QA Moves Left Without Abandoning the Right

A useful QA question is not only:

**"Does the implementation work?"**

It is also:

**"Before we build this, how could this agreement be misunderstood or
fail?"**

Give QA one happy-path example and you often get ten valuable questions
back.

What happens at the boundary?

What happens when data is missing?

When a dependency is slow?

When it returns 429 or 500?

During migration?

Under load?

How will we observe the failure?

Contract-Driven Development gives those questions somewhere to go.

Some become examples.

Some become simulations.

Some become executable acceptance checks.

Some become resilience or non-functional campaigns.

QA moves earlier into the formation of the agreement.

But real systems, exploratory testing and end-to-end validation remain
essential.

**QA moves left without abandoning the right.**

## 4. Don't Teach the Tools First

Want to introduce Contract-Driven Development?

Don't start with OpenAPI training.

Or Microcks.

Or BDD.

Or CI/CD gates.

Start with a painful real problem.

An integration that produces endless clarification.

A migration where the old system, consumers and new API disagree.

A feature whose business rules keep surprising everyone.

Then:

**Real problem → collaborative discovery → examples → agreement →
executable contract → tooling**

Now the technology solves a problem the team already understands.

This changes adoption completely.

And instead of a giant transformation program, try a small **change
lab**:

One real boundary.

One BA + QA + Dev group.

A few weeks of guided practice.

Then inspect the evidence.

What became easier?

What was discovered earlier?

What reduced rework?

What should become standard?

**Teach the problem-solving pattern before the toolchain.**

## 5. AI May Propose. Humans Agree.

AI can generate a surprising amount of software-development material.

Stories.

Examples.

API specifications.

Architecture models.

Tests.

Documentation.

So what happens to BA, QA and Developer roles?

A useful operating principle might be:

**AI may propose intent. Humans establish agreement. Automation verifies
it.**

The BA challenges whether generated artifacts reflect the actual problem
and desired outcome.

QA challenges assumptions, edge cases and failure conditions.

Developers challenge feasibility, architecture and implementation
consequences.

AI accelerates the production and exploration of candidate artifacts.

It should not silently become the authority that decides what the
software is supposed to mean.

The interesting transformation is therefore not:

**Human work → AI work**

It is closer to:

**Human reasoning + AI acceleration → explicit agreement → automated
evidence**

That feels like a much more sustainable model for AI-assisted
engineering.

## 6. Change the Collaboration, Then the System

There is an interesting symmetry in Contract-Driven Development.

We say important software expectations should become explicit and
verifiable.

Why not apply the same idea to the transformation itself?

Instead of:

**"Teams should collaborate better."**

Try agreements such as:

**Critical API changes are reviewed by affected consumers before
provider implementation.**

**Important business rules have concrete examples agreed by BA, QA and
Dev before coding.**

**Migration incompatibilities become explicit decisions instead of late
integration surprises.**

Now the change itself can produce evidence.

Are ambiguities found earlier?

Are clarification loops shrinking?

Are integration defects moving left?

Is rework falling?

The destination isn't a team where BA, QA and Dev all become the same
role.

It is a team where specialized expertise meets earlier around shared
intent.

**BA brings intent. QA brings challenge. Dev brings implementation.
Together, they establish the agreement.**

Don't transform the roles.

**Transform the collaboration.**
