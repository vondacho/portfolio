AI-driven specification journey

The Significant
Prompt

A problem narrative becomes a connected, reviewable delivery baseline

Reusable AI instructions · As-Code artefacts · Human review · Git source of truth

AI-assisted development often starts with a ticket and a repository. This journey starts with the reasoning that makes implementation correct.

A significant prompt asks AI to study a meaningful problem description and produce connected software-intent artefacts. Reusable instructions govern the generation. People review the meaning. Git records the accepted result.

A significant prompt turns a meaningful problem description into a connected delivery baseline.

The usual AI starting point

A ticket carries too little of the design reasoning

AI receives

Source code, a small work item, scattered prose, and implementation patterns.

AI must infer

User outcomes, domain rules, ownership boundaries, architecture constraints, and proof of correctness.

A coding agent can produce plausible code from a ticket and repository. Those inputs rarely explain why the change matters or which rules and constraints define correctness.

The missing reasoning increases the chance that AI implements the ticket literally while weakening the user journey, domain model, or architecture.

A repository and ticket rarely provide enough intent for dependable AI-assisted delivery.

Starting material

A meaningful account of the problem

NarrativeActors, goals, current journey, pain points, desired outcomes
EvidenceUX research, observed behaviour, production signals, stakeholder knowledge
ContextExisting systems, policies, constraints, contracts, and architecture
UncertaintyConflicts, assumptions, hotspots, and questions requiring decisions

The initial input may be a narrative, a consistent specification, or several evidence sources. The important property is enough context to distinguish facts from assumptions.

UX research supplies the outside-in experience. Domain experts explain business behaviour. Engineers describe existing constraints. AI must preserve unresolved points instead of completing the story with plausible inventions.

The source combines problem context and evidence while keeping uncertainty visible.

LLM instruction envelope

Doctrine, notation, and DSL govern generation

Doctrine

Purpose, quality criteria, preserved uncertainty, and decisions AI must not make.

Notation

Modelling concepts, relationships, annotations, and visual semantics.

DSL

Exact grammar and file format that generated output must satisfy.

These three sources form the practice-specific instruction envelope. Doctrine governs meaning. Notation teaches the model constructs. The DSL constrains the generated file and enables parser validation.

Notation protects syntax. Doctrine protects the practice. Together they reduce syntactically correct output that violates the intent of the workshop or model.

Doctrine governs meaning, notation explains the model, and the DSL constrains the generated file.

Analysis before generation

AI first produces a structured reading

Source evidenceNarrative, research, constraints, current models
Problem readingActors, outcomes, journey, vocabulary
UncertaintyAssumptions, conflicts, hotspots, questions
Generation planRequired artefacts, IDs, review roles

AI should not jump from the narrative to architecture. It first separates evidence from inference and identifies the gaps that need human decisions.

The analysis also proposes stable identifiers and explains which artefacts are justified. The goal is the smallest connected set that supports understanding and delivery.

AI separates evidence from inference before it generates the model set.

Experience and domain behaviour become explicit

Outside-in journey

Goals, stages, touchpoints, pain points, research evidence, and accessibility needs.

Domain flow

Big Picture, focused processes, system responsibility, pivotal events, and hotspots.

Journey Mapping preserves what the person experiences. Event Storming reveals the domain behaviour that produces or supports that experience.

AI proposes an `.eventstorm` hypothesis. Participants correct it in the synchronized visual tool. Doctrine prevents AI from resolving hotspots or inventing domain facts.

The journey captures experience while Event Storming reveals the behaviour behind it.

Tactical model

Aggregates, entities, value objects, events, policies, and meaningful invariants.

AI proposes boundaries from the language and responsibilities revealed earlier. It can expose inconsistencies and candidate seams.

Consistency becomes testable

Validation can find missing references, conflicting vocabulary, unowned components, unjustified interfaces, and delivery items without expected evidence.

Every practice answers a different question, so consistency does not mean identical models. It means explicit relationships and visible contradictions.

The manifest makes impact analysis and validation possible. A production signal can lead back through component, context, example, story, journey, and objective.

A traceability manifest turns cross-lifecycle consistency into something tooling can verify.

Walking skeleton

The first pack proves the technical delivery path

One scenarioMinimal end-to-end behaviour
ArchitectureCritical components and interfaces
DeliveryDeployment, contract checks, automated test
EvidenceObservability and production feedback

The walking skeleton targets technical learning. It exercises the smallest path that proves architecture, integration, deployment, testing, contract validation, and observability.

AI can derive the pack from connected models instead of inventing an isolated technical spike. The pack still records the source stories, examples, risks, and completion evidence.

The walking skeleton proves that architecture and delivery work end to end.

Minimum viable product

The second pack tests a meaningful outcome

Coherent slice

A complete path across the Story Map that delivers a recognisable user outcome.

Measurable learning

An explicit business or product hypothesis, accepted examples, and evidence that can support a decision.

The MVP differs from the walking skeleton. It focuses on a meaningful user outcome and an important learning hypothesis.

A set of high-priority tickets does not automatically form an MVP. The connected artefacts let AI propose a coherent journey slice with examples, context impact, architecture, tests, and operational measures.

The MVP delivers a coherent user outcome and produces evidence for a product decision.

Acceptance loop

Git records intent after people approve meaning

AI proposalArtefacts, packs, questions, provenance
ValidationDSL, references, semantics, compatibility
Human reviewDomain, product, UX, QA, architecture
GitOps loopTickets, tests, views, delivery, evidence

AI writes a branch and a pull-request description. Automated checks verify form and enforceable constraints. People decide whether the proposed meaning is correct.

After merge, Git becomes the source of truth. GitOps automation generates and reconciles downstream projections. Production evidence can trigger a new change through the same review path.

Validation checks the proposal, people approve the meaning, and GitOps keeps downstream consumers aligned.
