The discipline

The system-design decision

How will software responsibilities, interactions, and deployment choices realize product and domain intent?

System design connects semantic responsibility to technical structure. It should help each audience see the detail required for its decision without combining everything in one diagram.

Sources: C4 model, LikeC4, PlantUML, OpenAPI, and AsyncAPI.

System design explains how software realizes known intent and constraints.

C4 model

Levels of zoom support different decisions

ContextPeople, the system in focus, and external systems
ContainerApplications and data stores inside the system
ComponentResponsibilities inside a container
CodeOptional implementation detail when it adds value

The official C4 guidance defines four static levels and notes that context and container diagrams are enough for many teams. Use only the views that support a real decision.

Sources: C4 model, LikeC4, PlantUML, OpenAPI, and AsyncAPI.

C4 provides consistent zoom levels without requiring every possible diagram.

LikeC4

One architecture model generates many views

Model

Hierarchical elements, relationships, metadata, ownership, deployment.

Views

Projections for system overview, component interaction, data flow, and scenarios.

LikeC4 describes architecture as code and generates views from a shared model. That prevents each diagram from maintaining a separate copy of components and relationships.

Sources: C4 model, LikeC4, PlantUML, OpenAPI, and AsyncAPI.

The model is authoritative. Views project it for different questions.

PlantUML

Focused diagrams add behavioral precision

Sequence

Interaction order for one scenario.

State

Allowed transitions and lifecycle.

Class or component

Detailed structure where it helps implementation.

PlantUML supports many structural and behavioral diagram types from text. It complements the model-centric C4 views and should reuse the same element and contract references.

Sources: C4 model, LikeC4, PlantUML, OpenAPI, and AsyncAPI.

PlantUML adds precise scenario and structure views without creating new vocabulary.

Enforcement

Architecture rules enter the delivery pipeline

Critical elements have owners
Relationships state purpose and direction
Cross-context dependencies follow policy
Public interfaces link to contracts
Dynamic views use valid model elements
Sensitive changes require affected-owner review

The pipeline can lint the model, build diagrams, run policies, and publish accepted views. Errors should name the violated rule and responsible owner.

Sources: C4 model, LikeC4, PlantUML, OpenAPI, and AsyncAPI.

CI validates ownership, dependencies, interfaces, and view consistency.

Git and GitOps

Git as source of truth and architecture reconciliation

Git sourceModels, diagrams, ADRs, policies
Review and mergeAffected owners approve change
AutomationValidate and publish views
ReconciliationCompare declared and observed design

Git holds the accepted LikeC4 and PlantUML sources, Architecture Decision Records, policies, and interface links. Every rendered view identifies the model revision that produced it.

GitOps-style automation publishes safe projections and compares declared architecture with repositories, contracts, deployment data, and observed interactions. Structural differences create review work because runtime state alone cannot explain architectural intent.

Source: OpenGitOps principles.

Git governs declared architecture. Automation publishes views and detects differences that require design review.

Change management

Start with the views teams actually need

01Model

Create context and container views for one value stream.

02Link

Connect contexts, repositories, and interfaces.

03Validate

Add ownership and dependency rules.

04Publish

Generate views automatically with every accepted change.

Use live previews and clear validation errors. Ask teams to update the model in the same change that alters structure. Expand views only when a stakeholder needs them.

Sources: C4 model, LikeC4, PlantUML, OpenAPI, and AsyncAPI.

Start with useful views, connect them, add rules, and publish automatically.
